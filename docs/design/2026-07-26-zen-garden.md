## 1. 왜 바꾸나 — 두 개의 다른 문제가 붙어 있었다

지금 도구는 사실 성격이 다른 두 문제를 뭉쳐서 풀고 있다:

1. **디자인 공간 샘플링** — 가능한 스타일 중 30개를 어떻게 "잘 흩뿌리나"
2. **선택 UI** — 사람이 30개를 어떻게 훑고 고르나

지금은 (1)을 "이름 붙인 스타일 30개"로, (2)를 "갤러리 한 판"으로 푼다. 둘 다 더 나은 선행 사례가 있다:
- **CSS Zen Garden (2003)** — 이 문제의 원조. HTML 하나 고정, CSS만 바꿔 218개 디자인. 콘텐츠·구조 고정 → 스타일 비교가 사과 대 사과.
- **Midjourney 4장 그리드 → variation** — 넓게 뿌리고 → 하나 찍고 → 근처를 다시 뿌린다. 탐색과 수렴의 산출물이 다름.
- **Style Tiles / Element Collage** — 완성 화면 대신 조각판을 먼저 보여줌(레이아웃 불만 vs 톤 불만 분리).
- **선택 과부하** — 훑기는 30개도 괜찮지만 결정은 5~7개가 한계.

## 2. 지금 구조의 근본 문제

- 스타일마다 **HTML을 통짜 생성** → 모델이 마음대로 KPI 카드를 끼워넣을 수 있음 → 그걸 잡으려고 `archetype-lint`가 필요했던 것.
- `archetype-lint`는 **"내가 상상한 실패"만** 잡는다. 다음에 모델이 상상 못 한 방식으로 새면 → 사고 → 원인 분석 → 규칙 추가 — 이 사이클이 무한히 돈다.
- 원형 축에는 "**보고 고르기**"가 없다(스타일 축엔 있는데). 연서 사고가 스타일 축이 아니라 원형 축에서 난 게 우연이 아니다.

## 3. 결정 — 3층 Zen Garden

**DOM 하나 고정, CSS만 바꾼다. 그리고 CSS를 3층으로 쪼갠다.**

```
tokens/style-NN.css          변수만. 원형 무관.            30개 (영구 자산)
  :root{ --radius:0; --font:ui-monospace; --bg:#0a0c10;
         --shadow:none; --space:4px; --accent:#3fb950 }

base/archetype-X.css         토큰 먹는 일반 컴포넌트.       원형당 1개
  .bubble{ border-radius:var(--radius); box-shadow:var(--shadow) }

signature/style-NN--X.css    구조적 시그니처만.           일부 스타일만
  .bubble{background:none;border:0} .text::before{content:"연서 > "}
```

**곱셈이 덧셈이 된다:**

| | 원형 1개 | 원형 11개 | 원형 추가 비용 |
|---|---|---|---|
| 지금 (HTML 통짜) | 30 | 330 | **+30** |
| 순진한 Zen Garden | 30 | 330 | +30 |
| **3층** | 30+1+8 | 30+11+88 | **+9** |

### 왜 이 구조인지 — 효과 다섯

1. **검사 → 구조.** DOM이 고정이면 CSS에 KPI 카드를 *쓸 수가 없다*(없는 요소에 스타일 못 줌). illegal state를 표현 불가능하게 만드는 패턴. → `archetype-lint` 은퇴.
2. **P2(축)가 공짜.** 토큰 파일이 곧 좌표다(`--radius`=형태축, `--accent` 채도=채도축, `--space`=밀도축, `--shadow`=장식축). 파싱해 읽으면 지도가 **처방이 아니라 측정에서 emerge**. LHS 균등샘플링의 죽은구석 문제는 **MAP-Elites**(Mouret & Clune 2015)로 해결 — 아카이브 격자에 셀마다 최고 하나. **개수는 입력이 아니라 출력**이 된다.
3. **뭉친 7개를 자동 진단.** 03·16·21·22·24·25·29를 3층에 넣으면 시그니처 파일이 안 나온다(토큰만으로 표현되니까). 반대로 04·18·19는 시그니처가 필수. → **시그니처 파일 유무 = "겹친다"의 기계적 정의.** 눈대중 클러스터링이 파일 존재 여부로 떨어짐.
4. **MANUAL-ONLY 5개(19·21·23·25·28) 대부분 해소.** 구조가 고정되니 "구조를 못 지킴"으로 수동이던 것들이 자동화됨.
5. **모델 과제가 쉬워짐.** 토큰 파일 = 변수 12개 채우기(환각 여지 거의 0). 어려운 건 시그니처뿐이고 그건 원형당 8개, 커버리지 린트가 지킴.

## 4. T1 결과 — GO 확정 🟢

**테스트**: 신선한 에이전트에 **클래스 인벤토리 없이** 스켈레톤(`skeleton-B.html`)만 + "04 터미널" 브리프 → CSS만 받음. ("모델이 *남의* DOM에 스타일 입힐 수 있나" — 유일하게 GO를 뒤집을 수 있는 테스트.)

**판정 (PASS)**:

| 기준 | 결과 |
|---|---|
| 환각 셀렉터 | **0건** (실재 클래스 33개 전부 정확히 타겟) |
| 누락 영역 | **0건** (5개 data-region 다 스타일됨) |
| 프리픽스 시그니처 | **있음** (`::before` 24곳, `data-speaker`로 `연서 >`·`지민 $`, 모노스페이스·radius0·shadow none) |

- **결정적 증거**: 에이전트가 `.icon[aria-label="첨부"]`·`[aria-label="음성"]`까지 정확히 타겟 — 패턴매칭으론 못 나오는 셀렉터. **진짜 DOM을 읽었다는 뜻.**
- **`selector-coverage-lint` = `archetype-lint`의 후계자.** CSS가 저지를 수 있는 나쁜 짓은 딱 둘(① 환각 셀렉터 ② 누락 영역)이고 이 린트가 그 **전 집합**을 덮는다. "상상한 실패만" 잡던 걸 "가능한 실패 전부"로 교체.
  - 진화 1건: 처음엔 aria-label 셀렉터를 환각으로 오판(모델이 한글을 CSS 유니코드 이스케이프 `\CCA8\BD80`로 씀) → **린트에 CSS 이스케이프 디코드 추가**. 자가검증(심은 환각 3·누락 1)은 여전히 다 잡음.
- **정직한 한계**: N=1(터미널 1개·원형 1개). 증명이 아니라 **강한 증거**. 단 제일 빡센 재구조 케이스(버블 제거+프리픽스)였고 깨끗이 통과. 안전벨트: (a) 프롬프트에 클래스 인벤토리 첨부(공짜 보험), (b) 린트가 잔여 검출.

## 5. 원형 이름 — A~K → 동사 (내부 ID는 유지)

A~K는 내부 ID인데 UX로 새어나왔다. 유저가 "D가 뭐야"를 회상(recall)하게 하지 말고, 동사로 **재인(recognition)**하게. 코드·`_spec.json`은 A~K 유지, 사람 눈엔 동사.

| ID | 동사 이름 | 무엇이 주인공 | 언제 (유저 관점) |
|---|---|---|---|
| A | **훑어본다** | KPI·차트·표 | 여러 숫자를 한눈에 감시할 때 |
| B | **주고받는다** | 말풍선 흐름·입력창 | 메시지를 주고받을 때 |
| C | **읽는다** | 긴 본문 타이포 | 글 하나에 몰입할 때 |
| D | **고른다** | 카드 그리드·필터 | 여럿 둘러보고 하나 고를 때 |
| E | **채워넣는다** | 입력 필드·단계 | 칸을 채워 신청·제출할 때 |
| F | **흘려본다** | 시간순 스트림 | 끝없이 스크롤할 때 |
| G | **만든다** | 편집 영역·툴바 | 뭔가 만들거나 편집할 때 |
| H | **찾는다** | 검색어·결과 좁히기 | 검색해서 좁혀갈 때 |
| I | **처음 익힌다** | 슬라이드·진행 | 따라 하며 시작할 때 |
| J | **들어간다** | 단일 인증 카드 | 로그인·가입할 때 |
| K | **관리한다** | 행 밀도·토글 | 내 정보·설정을 손볼 때 |

### 이름이 뱉어낸 경계 문제

- **헷갈리는 삼각형: 고른다(D) / 흘려본다(F) / 찾는다(H)** — 셋 다 "여러 항목을 본다"의 변종. 텍스트 증거: Enrico 대응이 D=`List 265`, F=`List 일부`, H=`Search 35` — **F는 D와 같은 List 통에서 갈라냄.** "인스타 탐색탭=D냐 F냐"가 실무에서 안 갈림.
- **중복 후보: 들어간다(J) ⊂ 채워넣는다(E)** — J(로그인/가입)는 E(폼)의 특수 케이스. I(온보딩)도 입력 있으면 E, 설명 길면 C와 겹침.
- **커버리지 구멍 4개**:

  | 빠진 축 | 예시 | 지금 어디에 억지로 |
  |---|---|---|
  | 지도·공간 | 배달 추적·부동산 지도 | 없음 (진짜 구멍) |
  | 캘린더·일정 | 예약 캘린더·주간 일정 | E/D로 못 퉁침 |
  | 미디어 재생 | 영상·음악 플레이어 | G에 `MediaPlayer`로 억지 편입 |
  | 데이터 테이블 | 관리자 CRUD·스프레드시트 | A의 '표 컴포넌트'로 퉁침 |

  → 11개는 "선형 문서형 웹"엔 잘 맞고, **공간·시간·재생·표 4축이 약함**. 완벽할 필요는 없고 "**어디가 비었는지 아는 상태**"가 목적.

## 6. 원형 선택 UX — 게이트 → 취소버튼

- 게이트는 **되돌리기 비싼 결정**에 단다. 지금은 원형이 틀리면 HTML 30장 폐기(비쌈) → 게이트 필요. **3층에선 토큰 30개가 그대로 살아남음** → 스켈레톤 1 + 시그니처 8만 다시(쌈). **결정이 싸지면 게이트가 아니라 취소버튼**이 답.
- 수정된 흐름 — **멈춤 0회**:
  ```
  도메인/아이디어 입력
     ↓  AI가 원형 추론 + 스켈레톤 즉시 렌더 (질문 없음)
     ↓
  [ 스켈레톤 와이어프레임이 화면에 뜸 ]   ← 질문이 아니라 그림 (재인)
     대안 원형 2~3개는 옆에 작은 썸네일   ← 틀렸으면 클릭 한 번
     ↓  (아무것도 안 하면 그냥 진행)
  30 CSS → 갤러리
  ```
- **도메인 = 게이트 → 콘텐츠 팩으로 강등.** 카탈로그에 없으면 AI가 즉석 생성 → 커버리지 절벽 소멸. **단 진짜 콘텐츠는 양보 금지**(lorem으로 채우면 긴 제목·빈 상태에서 깨지는 스타일이 다 예뻐 보임 — 도메인 카탈로그의 유일한 존재 이유).
- `archetype-showcase.html`(원형 11종 나란히)이 이 콘택트시트의 8할. 여기에 동사 이름 라벨 붙이면 정적 버전은 즉시.

## 7. 미결 — T2·T3 (GO 안 건드림, 모양만 정함)

- **T2 정보구조 분기** (반나절): 사이드바 DOM 하나로 상단바 / 아이콘 레일 / 하단탭 3종 CSS 시도 → **"원형당 스켈레톤 몇 개 필요한가"** 확정. 예측: 통과하되 `.nav-icon`/`.nav-label` 분리 훅이 필요하다는 걸 알려줄 것. 진짜 못 넘는 건 "영역 개수가 다른 경우(2패널↔3패널)"뿐 → 스켈레톤 변형으로.
- **T3 토큰전용 변별력** (하루): 뭉친 7개를 토큰만으로 만들어 나란히 → **몇 개를 병합할지** 결정 (GO/NO-GO 아님).
- **(선택) 11컷 검증**: 실제 앱 40~50 화면을 A~K로 분류 → 못 넣는 게 나오면 원형 부족, 항상 헷갈리는 쌍이면 경계 오류. §5의 구멍·중복을 데이터로 확정.

## 8. 이대로 가면 — 최종 상태

```
skeletons/  archetype-B.v1.html      ← 얼린 계약. 원형당 1~2개, 필요할 때 저작
tokens/     style-01..30.css         ← 원형 무관. 영구 자산. 좌표이자 랄프 핸드오프물
base/       archetype-B.css          ← 원형당 1개
signature/  style-04--B.css …        ← 원형당 6~10개
lint/       selector-coverage.js     ← archetype-lint 후계자, 실패 전 집합 커버
map/        (토큰 파싱 → 좌표 → 빈 셀 감지)
```

| | 지금 | 이후 |
|---|---|---|
| 원형 결정 | 게이트 질문, 틀리면 30장 폐기 | 그림으로 확인, 틀리면 클릭 한 번 |
| 생성 실패 | 사고→원인분석→규칙추가(무한) | 두 종류뿐, 둘 다 자동 검출 |
| 한 스타일 재생성 | HTML 통째, 콘텐츠 틀어질 위험 | CSS 한 파일, 콘텐츠 불가침 |
| "겹치는 거 있냐" | 눈대중 | 좌표로 측정, 빈 셀만 재샘플 |
| 스타일 개수 | 30 고정 | 아카이브가 정함 |
| 랄프 넘기기 | HTML에서 시스템 역추출 | 토큰 파일 그대로 (역추출 불필요) |
| 원형 하나 추가 | 30개 재생성 | 9개 |

- **남는 공사**: 스켈레톤 저작이 진짜 공사이고 자동화 안 됨. 대신 **한 번에 11개 다 만들 필요 없음** — 도메인 쓸 때마다 필요한 원형 하나씩 lazily 저작, 토큰 30개는 첫 원형에서 만들어 이후 전부 재사용. 초기 공사는 생각보다 작음.
- **안 되는 것(솔직히)**: 영역 개수가 갈리는 스타일(2패널↔3패널)은 여전히 스켈레톤 변형 필요. 이건 WordPress가 테마(스킨)와 템플릿(구조)을 20년째 분리해온 이유 — 업계 정답이 "싸우지 말고 변형을 둬라".

## 부록 — Zen Garden(2003)에서 확인한 것

- **훅 스팬은 있었지만 지금은 쓰지 말라고 함.** 원본 HTML의 `extra1~extra5`는 과거 이미지용 캐치올이고, 요즘은 `::before`/`::after`가 완전 지원되니 그걸 선호(주석에 명시). → 우리 `.hook` 스팬 재검토. 모든 요소가 이미 `::before`/`::after` 2슬롯을 공짜로 가짐. **훅 스팬은 "어느 기존 요소에도 붙일 수 없는 위치"에만.** 훅 하나하나가 영원히 남는 계약이라 싸지 않음.
- **HTML은 절대 안 바뀐다 = 규칙이 아니라 물리법칙.** 하나의 HTML로 218개 디자인. → 천장 높음(30개는 여유). **스켈레톤은 얼리는 순간 계약** → `archetype-B.v1.html`로 버전 박고, 커버리지 린트를 회귀 테스트로(공짜).
